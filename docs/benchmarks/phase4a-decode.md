# Phase 4a: file decode into CUDA (`fmp decode`)

Scope (`docs/implementation-plan.md`, Phase 4, step 4a): FFmpeg demux and NVDEC decode into the application's CUDA
context, the NV12/P010-to-RGB convert kernel, the frame history, and `fmp decode` to verify a file against a software
decode. The pipeline (`fmp play`) is 4b.

Machine: RTX 5090, driver 620.70.06, Plasma 6.8 Wayland. System FFmpeg 9.0.2: libavcodec 63.1.102, libavformat
63.1.102, libavutil 61.1.102, with the `cuda` hwaccel. .NET 10.0.114 SDK; `fmp` is the NativeAOT binary from
`dotnet publish src/FrameMotionPlus.App -c Release -r linux-x64`. Clips are made by the ffmpeg CLI from `testsrc2`
(x264 `veryfast` with 3 B-frames for H.264, x265 `ultrafast` for HEVC Main10 with PQ/BT.2020 tags and HDR10 metadata).
Conditions of the published-binary runs: the desktop in use but idle (Discord, Chrome and NZXT CAM open, no video, no
game), load average 2 to 6 (the clips had just been encoded), GPU at P3, 0 % utilisation, 2.45 GB used by other
processes before each run. Numbers marked "harness" come from a small JIT console program over the same library
(`FrameMotionPlus.Sources.File`), not from `fmp`.

## Verdict

- **Decoded pictures are bit-exact with the software decode, and converted frames bit-exact with the CPU reference**,
  for H.264 8-bit (High, also High 10), HEVC 8-bit and Main10, AV1 (10-bit), VP9, B-frames, variable frame rate, a
  non-zero start, an elementary stream without timestamps, MPEG-TS (also two recordings concatenated, and one whose
  33-bit clock wraps), 640x360 up to 3840x2160 and 1366x766, limited and full range, BT.601, BT.709 and BT.2020: 21 clips
  in the tests, and the published binary's `--verify` on H.264 8-bit and HEVC Main10 at 1440p and 2160p (120 frames
  each), a 1080p MPEG-TS, a concatenated MPEG-TS and two elementary streams looping.
- **FFmpeg runs on the application's primary context** (`AV_CUDA_USE_CURRENT_CONTEXT`; the primary-context option is
  wrong for us, see below) **and on the source's copy stream**; the convert kernel reads FFmpeg's frame pool directly.
- **Per frame FFmpeg makes no context-synchronising call and no allocation**: one `cuvidDecodePicture`, one
  `cuvidMapVideoFrame64` (the host waits there for NVDEC; inside it, libnvcuvid records an event on the copy stream and
  `cuEventSynchronize`s on it: once per frame, on the decode thread), one unmap and two `cuMemcpy2DAsync` on the copy
  stream. Its frame pool would grow on demand; the source grows it to four buffers at start-up and checks every frame
  against them: growth after start-up was 0 in every run. Opening and closing do synchronise and free (below).
- **Decoding does not stall another thread's CUDA calls**: a thread launching kernels and recording events on its own
  stream saw a worst call of 0.015 to 0.041 ms while 1080p to 2160p decoded at full speed, the same as with nothing else
  running (0.023 to 0.110 ms). A context-synchronising free behind 100 ms of queued work, run as a control, holds the
  same probe for 100 ms.
- **What does block**: the decode thread itself, in `cuvidMapVideoFrame64` (0.35 ms per 1080p frame, 1.4 ms per 2160p
  frame), and behind any work queued on the copy stream (NVDEC waits for its one output surface) or ordered before it
  (the compute stream, a held buffer's release point). Hence the copy stream must be the source's alone; see "What the
  pipeline must know".
- **Cost**: decode 2,635 / 1,519 / 687 frames/s for H.264 8-bit at 1080p / 1440p / 2160p and 2,567 / 1,530 / 708 for
  HEVC Main10; the conversion 0.030 / 0.049 / 0.101 ms (8-bit) and 0.032 / 0.053 / 0.108 ms (10-bit) of GPU time per frame.
  A 4K60 file needs 16.7 ms per frame: about 1.4 ms of decode-thread time and 0.11 ms of GPU convert.
- **Zero managed allocations per frame** on the consumer (`TryRead`/`Release`) and on the decode thread, zero GC
  collections in steady playback, GPU memory flat over 25 loops, nothing leaked over 30 open/close cycles.

## One CUDA context

FFmpeg 9.0.2 offers three ways to get a CUDA device context (libavutil/hwcontext_cuda.c, read from the n9.0.2 sources):

- `AV_CUDA_USE_PRIMARY_CONTEXT` retains the device's primary context, **but insists on `CU_CTX_SCHED_BLOCKING_SYNC`**:
  if the primary context is already active with other flags (ours is, retained by `CudaContext.RetainPrimary` with the
  default scheduling) it fails with ENOTSUP ("Primary context already active with incompatible flags"); if it is not yet
  active it silently changes the flags with `cuDevicePrimaryCtxSetFlags`. Wrong for an application whose context exists
  first and whose scheduling mode is its own decision (the plan's open BlockingSync question).
- Filling `AVCUDADeviceContext.cuda_ctx` ourselves and calling `av_hwdevice_ctx_init` works, but leaves FFmpeg's private
  `cuda_device` at 0, which it uses for the texture-alignment query of its frame pool.
- **`AV_CUDA_USE_CURRENT_CONTEXT`** (used): `av_hwdevice_ctx_create` with the device's ordinal takes
  `cuCtxGetCurrent()`, sets the right device, and on teardown neither destroys nor releases the context. `MediaDecoder`
  makes the primary context current, creates the device context, checks `cuda_ctx == CudaContext.Handle` (refusing
  otherwise), and sets `AVCUDADeviceContext.stream` to the source's copy stream before the decoder exists.

Proven: `FFmpeg_uses_the_applications_context_and_the_copy_stream` (FFmpeg's context and stream are ours; the context's
reference count is unchanged after open and close), and every bit-exact RGB frame, converted by our kernel in our
context straight from FFmpeg's frame-pool pointer.

## What FFmpeg and NVDEC do in the context

### Per frame (traced)

An `LD_PRELOAD` shim interposed `dlsym`, so every CUDA-driver and NVDEC function looked up at run time came back
wrapped with counters and timers, attributed to the calling library: FFmpeg's own calls, and libnvcuvid's calls into
the CUDA driver (which the first version of this table missed: it wrapped FFmpeg's lookups only; the review's trace
found them). On the published binary, 1,200 frames (10 laps of a 120-frame clip, one open and close):

| Call | 1080p H.264: calls, mean | 2160p HEVC Main10: calls, mean | Notes |
| --- | --- | --- | --- |
| `cuvidDecodePicture` (FFmpeg) | 1,200, 15 µs | 1,200, 10 µs | submits the picture to NVDEC |
| `cuvidMapVideoFrame64` (FFmpeg) | 1,200, 349 µs (max 1.10 ms) | 1,200, 1,365 µs (max 4.3 ms) | **the decode thread waits here for NVDEC's decode**; output stream = the copy stream |
| inside it (libnvcuvid): `cuEventRecord`, `cuStreamQuery`, `cuEventSynchronize` | 1,202 / 1,201 / 1,196 in playback | 1,202 / 1,201 / 1,195 in playback | one each per frame, on the decode thread: an event on the copy stream after the map's work, and a host wait on it (mean 12 / 6 µs, max 0.33 / 0.24 ms here; the review measured mean 0.3 µs, max 106 µs) |
| `cuvidUnmapVideoFrame64` (FFmpeg) | 1,200, 0.0 µs | 1,200, 0.0 µs | |
| `cuMemcpy2DAsync_v2` (FFmpeg) | 2,400, 1.7 µs | 2,400, 1.9 µs | luma and chroma into a frame-pool buffer, **on the copy stream** (one stream handle seen) |

| `cuStreamSynchronize`, `cuCtxSynchronize` in playback | 0 | 0 | none |

| `cuMemFree_v2` (FFmpeg) | 4 | 4 | at close |

So the decode thread waits for the GPU once per frame inside NVDEC's map (on an event behind the copy stream's own
work), and opening and closing synchronise the context and free memory: both are drained points.

### The frame pool

FFmpeg 9.0.2's NVDEC path (libavcodec/nvdec.c) gives the decoder a dummy frames context (NVDEC's own decode surfaces,
created by `cuvidCreateDecoder`; `extra_hw_frames` only adds to their count), maps each output picture and copies it
(`av_frame_make_writable`) into a frame of a second, real CUDA frames context created with `initial_pool_size = 0`: an
`AVBufferPool` that allocates with `cuMemAlloc` whenever it is empty and frees only when the decoder goes. So neither
`initial_pool_size` nor `extra_hw_frames` can size it; what fixes it is the number of frames held at once. The source
holds a decoded frame only until its conversion is enqueued, so at most two are in use (one held, one being copied
into). With the first frame, at start-up, `MediaDecoder` takes three more frames from the pool and gives them back
(`av_hwframe_get_buffer`), so it holds four buffers before playback, and afterwards checks every frame's buffer against
those four: any other one would be a `cuMemAlloc` during playback and is counted (`FileSourceStatistics.PoolGrowth`,
reported by `fmp decode`, asserted 0 by the tests). It stayed 0 in every run; the trace shows the four allocations and
nothing else.

### Streams and blocking (measured, harness)

A 50 ms delay kernel was enqueued while decoding at full speed:

| Delay enqueued on | Host time of the next decode | Reading |
| --- | --- | --- |
| the copy stream | 49.3 ms, in `cuvidDecodePicture` (49.2 ms) | NVDEC waits for its single output surface, which the queued map and copy on the copy stream still use (FFmpeg's safe output mode: `ulNumOutputSurfaces = 1`) |
| the compute stream | 49.0 ms | through the source's own ordering: the copy stream waits for the previous conversion before FFmpeg's next copy |
| an unrelated stream | max 2.1 ms (no effect) | nothing context-wide |

So during playback the decode thread blocks on its own work (NVDEC's decode, the copy stream's queue, and through the
source's ordering the compute stream's), never on other streams, and makes no context-synchronising call; other threads
are not held up (next section). Its per-frame `cuEventSynchronize` waits on an event of the copy stream only.

## The convert kernel

`native/kernels/yuv.cu`, one thread per output pixel, pitch-linear output with an explicit pitch:

- **Chroma upsampled once, bilinearly, at its siting.** H.273's `chroma_sample_loc_type` places chroma at luma
  coordinates (ox + 2i, oy + 2j), ox ∈ {0, ½}, oy ∈ {0, ½, 1}; a luma column x is at chroma position (x − ox)/2, which in
  quarter samples is 2x − 2ox: each axis interpolates its two neighbours with weights (4 − f, f)/4, edges repeating the
  outermost sample. All six sitings; FFmpeg's `chroma_location` decides (unspecified: left, H.264/HEVC's default; the
  HDR10 clips are top-left). The interpolated chroma is kept exact, in 16ths.
- **Matrix and range exactly.** BT.601, BT.709 and BT.2020 non-constant luminance (Kr, Kb as the standards' decimals),
  limited or full range, 8- or 10-bit source. `YuvConversion` derives, on the host, integer coefficients from the
  closed-form inverse (R' = Y' + 2(1 − Kr)Cr, B' = Y' + 2(1 − Kb)Cb, G' = (Y' − Kr R' − Kb B')/Kg) over a common
  denominator, reduced by their gcd and checked against 64-bit overflow for every code; the kernel evaluates them in
  64-bit integers and rounds half up, clamped. No floating point, no approximation: each output code is the exact value
  round((2^m − 1)·R'). Transfer is untouched (SDR and PQ code values pass through; HLG stays HLG until Phase 7).
- 8-bit sources go to RGBA8, 10-bit to RGB10A2 (the kernel takes either output from either source).
- Cost: 0.030 ms at 1080p to 0.108 ms at 2160p (above).

**Why "bit-exact" is not self-fulfilling.** Three derivations agree bit for bit: the kernel (closed-form coefficients,
integer evaluation); the CPU reference `YuvReference` (App), which builds the *forward* matrix of the standards in exact
rationals, inverts it by Gauss–Jordan elimination, dequantises with H.273's equations and evaluates each channel over
its own denominator in 128-bit integers; and an exact oracle in the tests, which per pixel computes positions,
interpolation, dequantisation and the closed-form inverse with big rationals. The kernel equals the reference for 24
configurations × 6 sitings on random codes over the whole range (including illegal ones and the extremes), at sizes 1x1
to 1366x766, with pitched inputs whose padding would change the result if read and outputs inside guard bytes that stay
untouched; the reference equals the oracle on every pixel of a 9x7 image in every configuration and siting.

Against an independent implementation, zscale (the zimg library: the standards' coefficients in floating point, chroma
upsampled bilinearly from its siting, rounded to nearest without dither), told the same matrix, ranges and siting: every
value within 1 code (rounding at exact halves) and practically all equal, on a decoded frame of 8-bit BT.709 limited,
BT.601 limited and BT.709 full clips and a 10-bit BT.2020 top-left one (the test allows 1 code and under 0.1 % of values
differing). One detail: zimg upsamples an integer input's chroma in that integer format, rounding each interpolated
sample to a whole code, which on 10-bit input alone is up to 2 codes of RGB (measured against exact float arithmetic:
2.1); the test first widens 10-bit input to 16 bits with zimg's own depth conversion (an exact shift for limited
range), after which zscale is within 0.0002 codes of exact arithmetic. FFmpeg's swscale (accurate rounding, full chroma
interpolation) is kept as a secondary, looser check: 8-bit within 1 code (mean 0.001); 10-bit within 4 codes (mean
1.3), its 10-bit RGB (`gbrp10le`) topping out about 3 codes low (limited white 940 comes out near 1020 where H.273
gives 1023).

## Frame history, time and back-pressure

- `FrameHistory` holds `DecodeAhead + HistoryDepth` (4 + 3) RGB buffers, each with its own CUDA event as its `Ready`
  (recorded after its conversion, never re-recorded while a published frame names it), its content time and colour.
  A frame's `ColorMetadata` describes its RGB pixels: identity matrix, full range, the stream's primaries, transfer and
  HDR metadata (Core's convention, now written on `ColorMetadata`); the YCbCr matrix, range and siting it was converted
  from are the stream's (`FileStreamInfo.RawColor`, `.Conversion`) and, per frame, `FileFrameInfo.Conversion`. BT.601's
  primaries map to Core's new `Bt601Line525` / `Bt601Line625`.
  A buffer is written again only after the consumer released its frame with a GPU-side point
  (`FileFrameSource.Release(frameId, lastReader)`: the generator's `done`, a ring write, an event): the conversion stream
  waits on it (`cuStreamWaitEvent` or a semaphore wait) before overwriting, no CPU wait. Proven with a reader delayed
  300 ms on the GPU and a control without the signal (overwritten early).
- Decode output → convert → history: FFmpeg on the copy stream; the compute stream waits for the copy (event), converts
  and records the buffer's `Ready`; the copy stream waits for that conversion before FFmpeg's next copy, so a recycled
  pool buffer is never overwritten while it is read. The generator stream is 4b's.
- Content time: `best_effort_timestamp` minus the stream's start (or the first frame's), scaled exactly; a frame
  without one goes one frame duration after the previous (from the start again after a restart at the beginning).
  Within a lap, a timestamp that does not advance is either an **isolated collision** (less than one frame interval
  behind, and the previous frame was not repaired: moved 1 ns after the previous frame, counted, flagged
  `TimestampRepaired`) or a **discontinuity in the stream's timestamps** (a step back of a frame interval or more, or
  a second non-advancing frame in a row): the frame continues one interval after the previous one, is marked
  `Discontinuity` and flagged `TimestampJump`, and counted. So repairs never run together: two concatenated recordings
  used to squeeze the whole second one into 1 ns steps (30 frames of a 60-frame test clip). A **step forward of more
  than 10 s** (FFmpeg's own `dts_delta_threshold`) is marked and flagged the same way, so nothing interpolates across
  it, but its time is kept in a container with a continuous timeline (MP4/MOV, Matroska/WebM: a 12 s still is content
  and is held for 12 s) and collapsed to one interval only where libavformat says the format's clock may jump
  (`AVFMT_TS_DISCONT`: MPEG-TS, MPEG-PS; `FileStreamInfo.DiscontinuousTimestamps`). Loops and seeks also continue one
  interval after the last frame decoded.
  Distinct and strictly increasing, in presentation order. `FileFrameSource.TryGetFrameInfo` gives a held frame's media
  time, lap and events (`Loop`, `Seek`, `TimestampJump`, `TimestampRepaired`, `SeekFailed`); at the end without looping
  the queue drains and `IsEndOfStream` turns true (not while a seek is pending: it used to report the end when a seek
  was asked for there).
- Seeks: queued frames are dropped on the consumer side; the decoder restarts at the keyframe before the target (or,
  for an elementary stream, which has no time index, at its first byte, decoding forward to the target), drops frames
  before it, and the first frame at or after it is marked. FFmpeg 9.0.2's HEVC decoder keeps the frames its drain at
  the end of the stream had already queued for output across `avcodec_flush_buffers` (`hevc_decode_flush` clears the
  DPB, not `output_fifo`), and returned one of them first after a seek made while it drained (a frame from the end of
  the file, marked, then the target 1 ns later). The seek now receives and drops whatever the decoder still returns
  before it sends anything from the new position (`StaleFramesDropped`; the decoder also drops any frame that would come
  out before the first new packet). Those dropped frames are copied by FFmpeg into a frame-pool buffer like any other,
  so the restart is ordered behind the last conversion on the copy stream, as every receive is (without it a frame
  the consumer held could show the next one: a review found it). Tested by seeking from each of the last 16 positions
  of a clip, the decoder draining in some of them, for H.264, HEVC 8-bit and Main10, AV1, VP9 and MPEG-TS with a
  keyframe every second and with one keyframe only.
- MPEG-TS and MPEG-PS seeks: FFmpeg's timestamp search there takes every packet for a keyframe and lands on whatever
  packet is near the target's DTS. Loops therefore restarted at the second keyframe (a 90-frame clip with a keyframe
  every 30 looped with 60-frame laps) and a seek in a single-keyframe file delivered nothing. Every time seek is now
  checked: the first packet afterwards must be a keyframe at or before the target, else the seek goes back 1 s, 2 s,
  4 s, ... further; a target at or before the start, or a search that reaches it, restarts at the first byte where the
  format allows it (TS/PS and elementary streams; FFmpeg's byte seek starts at the first data byte), else at the
  start by time (an indexed container, which lands on its first keyframe). MP4 and Matroska seeks land on a keyframe at
  once, so they pay nothing.
- Loops: an elementary stream loops from its first byte (it used to stop the decode thread: no time index to seek
  with). An input that cannot seek at all (a pipe; FFmpeg's byte seek reports success there without moving) is not
  seeked: a seek is dropped and the next frame is marked `SeekFailed`, a loop ends the stream as if played once, both
  counted, `FileFrameSource.SeekError` says why; the decode thread never dies of it. A lap that yields no frame stops
  the looping instead of spinning.
- Back-pressure: at most `DecodeAhead` frames queued and no buffer reused before release; a slower consumer makes the
  decode thread wait, so no source frame is ever dropped. The wait is an event set by the consumer's reads and releases,
  a seek and `Stop`, not a timed poll: the decode thread made 0 context switches in 500 ms with a full queue and at the
  end of the file (it used to wake every millisecond: 495).

## What the pipeline must know (4b)

1. **The copy stream is the source's alone, and nothing heavy goes on the compute stream ahead of a conversion.** The
   decode thread blocks inside NVDEC (its per-frame `cuEventSynchronize`) behind anything queued on the copy stream
   (NVDEC's one output surface) and, through the source's own ordering, behind anything queued on the compute stream
   before a conversion, and behind a held buffer's release point: **whenever the compute stream is held, decoding
   stops.** The generator stays on its own stream.
2. **The decode thread spends 0.35 to 1.4 ms per frame waiting for NVDEC** (1080p to 2160p); the decode-ahead queue
   absorbs it. 4K60 leaves more than 15 ms per frame.
3. **Opening, closing, a mid-stream resolution or format change belong to a drained point.** Open creates the decoder
   (13 to 15 ms; libnvcuvid synchronises the context and frees memory in it) and grows the pool; close destroys it
   (libnvcuvid synchronises and frees again) and frees the pool (`cuMemFree`). A resolution change inside the stream
   makes FFmpeg re-create its decoder and pools (frees and allocations on the decode thread) before the source sees the
   new size; the source then fails with a clear message (`a size change mid-stream is not supported`), and 4b must treat
   that as a teardown.
4. **Release with a GPU point.** `IFrameSource.Release(frameId)` cannot carry the generator's `done`;
   `FileFrameSource.Release(frameId, lastReader)` does. Core's interface should gain the signal.
5. **Content time is media time plus `FileSourceOptions.ContentTimeOriginNs`**: 4b sets the origin to put it on
   `CLOCK_MONOTONIC`. Generators now refuse a pair whose content times do not increase.
6. The consumer must keep reading after a seek (stale frames are dropped as it reads them) and must not hold more than
   `HistoryDepth` frames, or decoding waits.
7. Pass the source's `NotifyDiscontinuity(frame.ContentTimeNs)` to the generator when a frame arrives with
   `Discontinuity` (a loop, a seek, a jump in the stream's timestamps); any thread, any time before the pair across it
   is enqueued. Treat a discontinuity's content time as a new origin for pacing, not as a long frame.
8. **After a seek the content time advances by (frames dropped + 1) intervals**, not one: frames queued before the
   seek had their content times assigned when decoded and are dropped unseen. Not changed: only the consumer knows which
   of them it read, and a decode-side rebase from the consumer's last frame would race with a read in progress.
9. **Matroska timestamps are whole milliseconds**: a 60 fps file's frames come 16, 17, 17 ms apart. That is not a
   variable rate (`fmp decode` allows two ticks of the time base) and should not be "corrected" by pacing.
10. **A release point must stay alive, and complete.** The event or semaphore passed to `Release` must outlive the
    source's next write of that buffer (until the source is stopped or disposed); destroying it earlier stops the decode
    thread with an error naming the frame and the rule. One that never completes holds the decode thread inside NVDEC
    for good: `Stop` gives up after 10 s with a `TimeoutException` saying so, and `Dispose` then frees nothing (freeing
    under the thread would crash it) and says so (`FileFrameSource.Leaked`); a later `Dispose`, once the GPU work has
    completed, frees everything.
11. **Frames are RGB and say so.** A frame's `ColorMetadata` is Core's convention, now written on `ColorMetadata`:
    identity matrix, full range, the content's primaries, transfer function and HDR metadata. The YCbCr matrix, range
    and siting it was converted from are the source's (`FileStreamInfo.Conversion`, `FileFrameInfo.Conversion`); the
    presenter and generators must not apply a YCbCr matrix to these frames.
12. **Gaps.** A forward step of more than 10 s between frames is always a discontinuity (marked: no interpolation
    across it). In MP4/Matroska its time is kept (hold the last frame for the gap); in MPEG-TS/PS it is collapsed to one
    frame interval. A jump back is always continued one interval on.
13. **MPEG-TS/PS seeks cost more**: a seek may take several demuxer seeks (backing off 1, 2, 4 s ... until it lands on
    a keyframe) and, in a file with very long GOPs, end in a restart from the first byte that decodes forward to the
    target (a deep seek into a long single-keyframe TS decodes everything before it). Keyframes are recognised by the
    parser's key flag; an MPEG-PS file is handled like TS but not in the tests.
14. **A file that grows while it plays** (a recording still being written) is untested: the end of the file is where
    demuxing first hits it.
15. **`TryReadTiming` is the consumer's**, like `TryRead`. While the decode thread is not running it collects timings
    itself; a gate keeps it and the decode thread from collecting at once, so a `Start` racing it from another thread is
    safe.

## Phase 4 backlogs (settled first)

- **Generator 1 (`TryConfigurePrepared`)**: the active instance and the configuration it is checked against are one
  immutable object (`VfgActivation`) published with one write and read once per `Enqueue`; safe from a control thread
  while the generator thread enqueues. Test: `Switching_prepared_instances_from_another_thread_during_enqueues_never_faults_one`
  (fails on the Phase 3 code within about 10 enqueues: `NVCV_ERR_MISMATCH`, a healthy instance faulted).
- **Generator 2 (`DiscontinuityLatch`)**: a notification names the first frame after the cut by content time; a pair is
  discontinuous when it spans it; the first pair starting at or after it releases it; up to four pending; generators
  refuse pairs whose content times do not increase; `fmp pattern` and the VFG commands give real content times.
- **Generator 3**: `IFrameGenerator.Enqueue`'s failure contract says what a failing call may have left (waits, a partly
  written output) and what the pipeline does with the slot.
- **Bridge 1 to 3**: the reaper frees nothing on a context while another of its entries there is not done; a bridge
  disposed or reconfigured after the presenter let go releases from CUDA and queues no GPU-side wait; the last bridge's
  Dispose frees what is done at once. Tests: `BridgeBacklogTests` (each fails on the Phase 2/3 code: a constructor held
  3 s, a free blocked for good, an import held while a restarted bridge is live).

## Review fixes (second pass)

An independent review found the following; each fix has a test that fails on the first-pass code (run against a
snapshot of it, with the test cut down to the APIs that code has).

- **A test read a process-wide counter in parallel** (`FFmpeg_uses_the_applications_context_and_the_copy_stream`: the
  context's reference count, which every stream and event in the process moves). Moved into the serial collection with
  the other process-wide measurements (`SerialSourceTests`). The other test projects touched were audited: Gpu, Vfx and
  Vulkan run without parallelisation, the Cuda and Core counter tests are already serial, and `DecodeCommandTests`
  assert only per-thread allocation counts. On the old code, with another thread creating streams meanwhile: 6 expected,
  8 found.
- **A stale HEVC frame after a seek while the decoder drained** (above, "Seeks"). Old code: the seek sweep fails for
  HEVC 8-bit and Main10 (the first frame not the target, the next 1 ns later) and, for every codec, reports the end of
  the stream right after a seek asked for at the end (a second bug the sweep found).
- **Runs of 1 ns repairs**: timestamp jumps are discontinuities (above, "Content time"). Old code: frame 30 of the
  concatenated clip unmarked, 30 steps of 1 ns; the late one a 99 s gap.
- **A failed seek stopped the decode thread; elementary streams could not loop** (above, "Loops"). Old code: the decode
  thread fails at the first loop or seek of a raw H.264 stream.

- **`--verify` failed on MPEG-TS** (ffprobe lists the stream twice): the first line is the answer. Old code: an internal

- **The verdict left checks out**: it now fails, naming each reason, on frames the software decode has beyond ours at

## Not done, or not clean

- The decode→copy span includes the copy stream idling while the host is in FFmpeg; NVDEC's own decode time is not on
  a CUDA stream and cannot be timed with CUDA events. The plane copy alone is 6 to 26 µs.
- Mid-stream resolution and format changes are refused, not handled (see 4b item 3).
- Unspecified standard-definition primaries stay `Unspecified` (BT.601 has two sets and the stream does not say
  which). Bit depth and chroma siting are in `FileStreamInfo`, not in Core's `FrameSourceInfo`.
- FFmpeg's error log ring (quoted in error messages) is process-wide: with two sources opening at once, one's message
  may quote the other's FFmpeg lines.
- Windows and other architectures: builds, reports file playback unavailable (layouts verified on x86-64 Linux only).
- The stall measurements are from one quiet desktop; the probe's 10 µs histogram buckets bound p99.9 from above.
